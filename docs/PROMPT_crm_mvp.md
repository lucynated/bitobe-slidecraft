# Slidecraft BITOBE — MVP за один день

Скопируй весь этот текст в Claude Code, открытый в папке `slidecraft/` (рядом лежат файлы из стартового набора).

---

## Роль и цель

Ты собираешь для консалтинговой компании BITOBE рабочий MVP системы, которая собирает презентации из уже существующих слайдов. Сегодня нужно показать принцип на живых данных:

1. забрать презентации из CRM (КП, отчёты, материалы сессий);
2. разложить их на слайды и убрать дубли;
3. описать каждый уникальный слайд карточкой по смыслу (полная классификация из `taxonomy.md`);
4. по текстовому запросу подобрать слайды, согласовать карту слайдов с человеком и собрать презентацию;
5. показать на прошлых выигранных КП, что подбор совпадает с тем, что реально ушло клиенту.

Это MVP: важнее, чтобы вся цепочка работала от начала до конца, чем полнота и красота. Где можно упростить без потери принципа, упрощай и записывай упрощение в `NOTES.md`.

## Ограничения MVP

- Источники: сделки за последние 12 месяцев, не больше 40 сделок (в приоритете выигранные, затем проигранные) и банк слайдов `seed/bank/`. Всего не больше ~600 исходных слайдов из CRM.
- CRM только читаем. Никаких записей, изменений и удалений в CRM.
- Ключ API храни в `.env` и никогда не выводи его в терминал, логи или файлы. `.env` добавь в `.gitignore`.
- Файлы клиентов не покидают компьютер, кроме обработки тобой. Не загружай их ни в какие внешние сервисы.
- Модели: основной агент — Opus. Карточки слайдов пишут субагенты на Sonnet пачками по 40 слайдов, параллельно по 4. Opus выборочно проверяет 10% карточек и решает спорные дубли.
- **STOP-GATE.** Перед каждым шагом, который тратит много лимитов или трогает CRM, покажи план и цифры и жди «ок». Это шаги 1, 4 и 6.

## Шаг 0. Вопросы человеку (STOP)

Задай одним сообщением и дождись ответов:
1. Какая CRM (Битрикс24, amoCRM, другая) и где лежат презентации: во вложениях к сделкам, в делах или комментариях, на Диске CRM?
2. Способ: **А** — файлы уже синхронизированы в папку на компьютере (например, через приложение Битрикс24 для компьютера) или **Б** — выгружаем через API?
3. Для варианта Б: ключ уже в `.env`? Подскажи, как его создать с правами только на чтение (для Битрикс24 — входящий вебхук с правами CRM и Диска на чтение; для amoCRM — интеграция с токеном).
4. Какие воронки и стадии считаются «выиграна» и «проиграна»?

Проверь окружение: Python 3, `python-pptx`, LibreOffice (`soffice`), `pdftoppm` (poppler). Если чего-то не хватает, дай команды установки под ОС человека и дождись установки.

## Шаг 1. Сбор файлов из CRM (STOP перед массовой выгрузкой)

**Вариант А — синхронизированная папка.** Найди в указанной папке все `.pptx`, `.ppt` и `.pdf` (PDF только если это презентация: горизонтальные страницы). Копируй их в `sources/crm/`, оригиналы не трогай. Сведения о сделке восстанови из пути и имени файла. Чего не хватает, оставь пустым и перечисли в `NOTES.md`.

**Вариант Б — API.**
1. Изучи официальную документацию REST API этой CRM: как получить список сделок с фильтром по дате и стадии и как получить файлы, прикреплённые к сделке (поля сделки, дела и комментарии, Диск). Выбери самый простой надёжный путь.
2. Напиши `scripts/crm_export.py`: только чтение, пауза между запросами, повтор при ошибках, продолжение с места остановки, пропуск уже скачанных файлов.
3. **Пробный запуск на 1 сделке.** Покажи, что скачалось и как заполнился `manifest.csv`. STOP, жди «ок».
4. Полный запуск в пределах ограничений MVP.

В обоих вариантах на выходе `sources/crm/*.pptx` и заполненный `sources/manifest.csv`. Старые `.ppt` сконвертируй в `.pptx` через LibreOffice. Покажи итог: сделок, файлов, выиграно/проиграно, по отраслям.

## Шаг 2. Извлечение (скрипт, без ИИ)

`scripts/extract.py`: для каждого слайда каждого файла (включая `seed/bank/`) сохрани:
- текст по фигурам, таблицы, заметки докладчика → `work/<file>/<n>.md`;
- картинку PNG (pptx → pdf через `soffice --headless`, затем `pdftoppm -r 60`);
- `text_hash` — хэш нормализованного текста (нижний регистр, без пробелов, цифр и дат);
- `img_hash` — перцептивный хэш картинки (`imagehash.phash`);
- источник: файл, номер слайда, данные сделки из manifest.

## Шаг 3. Дубли (скрипт + немного ИИ)

`scripts/dedup.py`, три уровня:
1. **Точные копии:** совпадают `text_hash` и `img_hash` (расстояние ≤ 4). Склеивай автоматически.
2. **Почти копии:** сходство текста ≥ 0,85 (SequenceMatcher или шинглы) или расстояние `img_hash` ≤ 10. Группируй. Основной слайд — самый свежий по дате сделки, при равенстве — из выигранной сделки. Остальные записывай как `versions`, не удаляй.
3. **Смысловые варианты** ищи после карточек (шаг 4): внутри одной темы и одного типа сравни тезисы и отметь `variant_of`.

Важное правило: у каждого уникального слайда храни список всех мест, где он встречался (`sources`: файл, сделка, стадия, дата). Это сигнал популярности и эталон для проверки.

Слайды из `seed/bank/`, которые совпали с `seed/catalog_bank.json`, не описывай заново: перенеси готовую карточку и дополни новыми полями.

Итог — `library/dedup_report.md`: сколько исходных, точных копий, почти копий, уникальных, по типам файлов. Покажи цифры.

## Шаг 4. Карточки (STOP перед запуском: покажи число уникальных слайдов и оценку расхода)

Схема и допустимые значения — в `taxonomy.md`, соблюдай строго. Субагенты на Sonnet, пачки по 40 слайдов, на вход текст, заметки, картинка и данные источника. Главное поле — `thesis`: какую мысль слайд доказывает, а не что на нём нарисовано.

Затем Opus:
- проверяет случайные 10% карточек и исправляет системные ошибки во всех карточках сразу;
- размечает `variant_of` (шаг 3, уровень 3);
- пишет короткий индекс `library/index.jsonl` (≤ 40 слов на слайд) для первого прохода поиска.

## Шаг 5. Приложение (локальная страница)

Возьми `seed/page/build_page.py` и `template.html` как основу (они уже работали на банке) и доработай `app/index.html`:
- каталог: превью, тезис, когда ставить, фильтры по всем полям `taxonomy.md`, поиск по смыслу (по словам в тезисе, когда ставить и темах), переключатели «скрыть данные клиентов», «скрыть заготовки», «только из выигранных»;
- раздел «Дубли и варианты» с рекомендациями;
- раздел «Подборы»: показывает карты слайдов и результаты ретро-теста из `decks/`.

Страница открывается двойным кликом, без сервера (данные вшиты в HTML, картинки по относительным путям).

## Шаг 6. Подбор и сборка (главное для демонстрации)

Создай команду проекта `.claude/commands/podbor.md`, которая принимает запрос в свободной форме (аудитория, задача, формат, длительность, клиент) и делает следующее:

1. **Сюжет.** Пишет 5–9 тезисов выступления под запрос: открытие → проблема → решение → доказательство → детали → следующий шаг.
2. **Первый проход.** По `index.jsonl` и фильтрам (формат, аудитория, без чужих клиентских данных, если не сказано иное) отбирает 60–120 кандидатов.
3. **Второй проход.** Читает полные карточки кандидатов и подбирает по 1 слайду на тезис. Предпочитает основные слайды из выигранных сделок. Для пропусков ищет типовой макет (`type: макет`), который можно заполнить текстом.
4. **Карта слайдов (STOP).** Таблица: № | тезис | слайд (id, превью) | почему | что поменять (обезличить, обновить цифры, заполнить макет) | источник. Сохраняется в `decks/<дата>_<запрос>.md`. Жди «ок» или правок.
5. **Сборка.** Копирует выбранные слайды из исходных файлов в одну колоду `decks/<...>.pptx`. Все файлы на шаблоне BITOBE, поэтому переноси слайд вместе со связями и медиа и сопоставляй раскладку по имени. Если для какого-то слайда перенос не удаётся, вставь его картинкой с пометкой и запиши в карту. Текст в макетах заменяй, геометрию сложных схем не перестраивай. Если в проекте есть PPTX-Skill BITOBE, используй его правила сборки.
6. **Проверка.** Отрисуй собранную колоду в PNG, просмотри каждый слайд (наложения, чужой клиент, плейсхолдеры) и перечисли, что поправить вручную.

## Шаг 7. Ретро-тест на выигранных КП (доказательство принципа)

Возьми 3 выигранные сделки с КП из 8+ слайдов, исключённые из поиска на время теста. Для каждой сформулируй запрос только по данным сделки (клиент, отрасль, услуга, название) и прогони `/podbor` без шага сборки. Сравни карту с реальным КП:
- доля совпавших слайдов (с учётом версий и вариантов);
- какие слайды агент взял вместо реальных и равноценна ли замена;
- чего не нашёл и почему (нет в банке, слабая карточка, не тот тег).

Результат — в `decks/retro_test.md` и в раздел «Подборы» на странице. Совпадение 40–60% для MVP — хороший результат, если замены осмысленные.
